# Configuring a deployment

A deployment is configured in several places: the sheppy manifest, its
profiles, the module images, a module's saved state, and the robot itself.
This page says which place each kind of setting goes in, so a value is set in
one place only.

## Where each setting goes

| Setting                                     | Where it goes                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Which alternative of a node runs            | the manifest's `alternatives`, and a profile's `selections`                                                      |
| A node parameter and its default            | the alternative's `params:` in the manifest                                                                      |
| A parameter value for one robot             | that robot's profile, `profiles/<robot>.yaml`, under `overrides`                                                 |
| A parameter value for one run               | `p` in the TUI                                                                                                   |
| Large configuration that rarely changes     | a file in the module's image, chosen by a parameter                                                              |
| A value the module saves and reloads        | `~/.config/<module>`, mounted at `/config` (see [Storing state across runs](/patterns/storing-state-across-runs)) |
| Host and device setup that sheppy cannot do | `config/robots/<robot>/` next to the manifest, applied by a script                                               |
| Per-robot data a node reads as a file       | `config/robots/<robot>/`, mounted into the node through `config/robots/current`                                  |

### Parameters

Put a parameter in `params:` if anyone might change it for a robot or from the
TUI, with its default. A profile override or a TUI edit only applies to a
parameter listed there. A value hard-coded in `command:` can only be changed
by editing the manifest.

```yaml
# sheppy-manifest.yaml
- id: curobo_planner_nightly
  kind: docker
  ros_node_name: rammp_curobo
  container:
    image: ghcr.io/rammp-org/rammp-curobo:nightly
    command:
      - /opt/rammp_curobo/rammp_curobo_ros/lib/rammp_curobo_ros/planner_node
  params:
    config: gen3_real.yaml
    world: world_real_bench.yaml

# profiles/flatbot.yaml
overrides:
  planner:
    world: world_empty.yaml
```

### How parameters reach the node

For a docker alternative, sheppy writes `params:` to a ROS params file, mounts
it at `/sheppy/params.yaml`, and appends
`--ros-args --params-file /sheppy/params.yaml` to the container's command.
Three things follow:

- **Name the node when it matters.** The file is keyed by `ros_node_name`, or
  by the wildcard `/**` without one. Set `ros_node_name` when a parameter must
  land on one particular node. For example, the arm's `arbitration_mode` is
  read-only after launch.
- **Give a command.** With no `command:`, the appended arguments _replace_ the
  image's CMD. That works only when the image's entrypoint runs the node
  itself, as the camera images' does. Otherwise, write the command out, ending
  at the node's executable.
- **Not `ros2 launch`.** `ros2 launch` rejects the appended arguments
  (`unrecognized arguments: --ros-args`), and the container exits at start. An
  alternative that runs a launch file takes no `params:`, and its values are
  launch arguments in `command:`.

`params:` on a `process` alternative is ignored. Its `command` runs verbatim.
rammp-deployments' `validate_manifest.py` and a module's
`validate_fragment.py` reject these cases in CI.

### Robot setup

Some setup has to be done before any node starts, and sheppy has no way to do
it: the host's network interfaces, or the network settings a camera stores on
the device. That goes in `config/robots/<robot>/`, one file per kind of
setup. Each file has a script that applies it. The script:

- checks the whole file before it changes anything;
- changes only what differs, so running it twice is safe;
- has `--dry-run`, which prints the changes without making them;
- has `--validate`, which checks the file and exits. CI runs it on every
  robot.

Some per-robot data is read by nodes as a file: the arm's mount rotation, and
the fixed and calibrated transforms. It goes in the same directory.
`scripts/set_robot.py` makes a robot the host's active one by pointing
`config/robots/current` at its directory. The nodes that need it bind-mount
`./config/robots/current` read-only at `/config/robot`. Only data that is a
file by nature goes here, such as a URDF input or a calibration result. A
single value is a parameter.

Use the same robot name in `config/robots/<robot>/` and in
`profiles/<robot>.yaml`.

## Example: flatbot

flatbot is a mobile test platform. Its setup lives in rammp-deployments, in
`december_2026/config/robots/flatbot/`:

- `network.yaml` sets the Jetson's two network interfaces: a static address
  on the link to the arm, and DHCP on the sensor network.
- `oak_d.yaml` sets the network config of each OAK-D PoE camera. Each entry is
  named after the camera's node in the manifest, and the script finds the
  camera by its device ID.
- `mount.yaml` is the arm's mount rotation (30° forward lean).
  `arm_state_publisher` renders the arm's model from it.
- `transforms/cameras.yaml` holds the camera mounts, which the `static_tf`
  node publishes on `/tf_static`. A solved calibration replaces it.

After the Jetson is reflashed, three commands restore the setup:

```bash
uv run scripts/network_config.py december_2026/config/robots/flatbot
uv run scripts/oak_d_config.py   december_2026/config/robots/flatbot
uv run scripts/set_robot.py      december_2026/config/robots/flatbot
```

`profiles/flatbot.yaml` selects its alternatives and overrides the planner's
`world`.

## What does not go in `config/robots/`

- **Node parameters.** They go in the manifest's `params:` and in profiles.
- **Config files that are the same on every robot.** Ship them in the
  module's image, and choose between them with a parameter.
- **Saved state**, such as a calibration the operator ran. See
  [Storing state across runs](/patterns/storing-state-across-runs).
- **Secrets.**
