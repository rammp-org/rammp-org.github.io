# How-to guide

This guide walks through how to run and develop on the RAMMP software
ecosystem.

{/* LINK SUGGESTION: if a reader lands here without context, the lead is the
    place to send them to [Introduction](/) or [The platform](/platform) for
    what RAMMP is before they start installing things. */}

<Callout type="info">
  By the end of this guide, you will be able to build and publish a docker
  image that can run new applications on the RAMMP hardware! Setup for getting
  the base docker images running should take about 20 minutes.
</Callout>

## Prerequisites

Docker isolates everything inside the image, but the machine you run it on must
have the correct CPU architecture and, for `rammp-cuda`, the GPU driver.

**`rammp-base`** runs on any `arm64`/`aarch64` host with Docker — a Jetson, but
also an ARM Mac (inside an `arm64` Linux VM / Docker Desktop) or an AWS Graviton
instance, since it needs no GPU. It will not run on an x86 machine: there is no
`amd64` variant, and you get `exec format error`.

**`rammp-cuda`** runs only on a Jetson Orin with JetPack 6.1 or newer (L4T
`r36.4+`). JetPack 6.0 (L4T `r36.2`/`r36.3`) does not work: its driver is CUDA
12.2/12.4-era and cannot back this image's CUDA 12.6 runtime. Check the host
with `head -1 /etc/nv_tegra_release` — it must report `R36`, revision 4 or
later.

### Docker

Every node in the RAMMP system runs as a Docker container, which allows each
node to run their own dependencies and environment variables independently of
all other containers. Installation instructions are here:
[https://docs.docker.com/engine/install/ubuntu/](https://docs.docker.com/engine/install/ubuntu/)

## RAMMP base images

The RAMMP system provides base images that run on the RAMMP hardware so that
every module has the same ROS 2 version and the same core dependencies.

### `rammp-base`

ROS 2 Humble, Cyclone DDS, and `RAMMP-interfaces` compiled in. Use this for
**hardware drivers and light sensor nodes** — anything that doesn't need the
GPU.

{/* LINK SUGGESTION: "RAMMP-interfaces" is the natural anchor for a link to
    [Interfaces](/interfaces) — the reader will want the topic and message-type
    map right at this mention. */}

### `rammp-cuda`

Everything in `rammp-base`, plus the CUDA 12.6 runtime libraries and
CUDA-enabled PyTorch. **Only use it if your node needs the GPU**; it is several
gigabytes larger.

<Callout type="warning">
  If you build a module `FROM rammp-cuda`, remove `torch`/`torchvision` from
  that module's `requirements.txt`. Reinstalling them from PyPI replaces the
  Jetson-specific wheels with ones that cannot drive the GPU.
</Callout>

### Build and test locally

```bash
git clone https://github.com/rammp-org/RAMMP-docker.git
cd RAMMP-docker

make base          # rammp-base:1.0.0-jp6 (+ :humble)
make cuda          # rammp-cuda:1.0.0-jp6 (+ :humble)
make test          # smoke-test both images
```

`make test` runs `scripts/smoke-test.sh` against each image. It checks that the
image is arm64, that Cyclone is the selected middleware, that all eleven
interface types resolve and import, and — on the Jetson — that
`torch.cuda.is_available()` is true, that the GPU reports **sm_87**, that a
matmul and a cuDNN convolution actually execute, and that two containers can
discover each other over DDS.

### How to publish

Tag a release and CI does the rest — it builds both images on GitHub's native
arm64 runners, smoke-tests them, and pushes to GHCR:

```bash
git tag v1.0.0-jp6
git push origin v1.0.0-jp6
```

CI rejects a tag that doesn't match `v<semver>-jp<N>`, so a mistyped tag fails
the build instead of publishing an image whose tag doesn't say what JetPack it
targets. A prerelease slot is allowed for rehearsals, e.g. `v1.0.0-rc1-jp6`.

Pushes to `main` build and test but publish nothing, so only a tag can change
what is in the registry. To publish by hand from the Jetson instead:

```bash
docker login ghcr.io
make push
```

Images pushed to the registry can be pulled by the Jetson running on RAMMP.
Published images should follow our versioning conventions so that Sheppy is
able to pull the appropriate image.

{/* LINK SUGGESTION: "our versioning conventions" wants to be a link — to

1. Copy `templates/module.Dockerfile` to your module repo root as `Dockerfile`,
   and `templates/dockerignore.txt` to `.dockerignore`.
2. Replace `<your_module>`, pick the base (`rammp-base` unless you need the
   GPU), and **pin the version** in `FROM`.
3. Put your node package — and any task-specific interface package — in the
   repo. They build automatically into `/module_ws`, an overlay on top of the
   base; the robot interface comes from the base image and is not rebuilt.
4. Set the `CMD` to your launch file or `ros2 run` target.
