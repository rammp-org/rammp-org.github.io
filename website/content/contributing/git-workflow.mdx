# Git workflow

This is how we recommend building software for RAMMP. Having multiple people
across multiple organizations developing code can lead to a lot of headache
and can introduce unexpected bugs during integration. The goal of this
workflow is to:

- **Ensure code stability:** We always want a stable, working version of each
  repo ready to deploy. New contributions should never prevent us from testing
  existing functionality.
- **Maintain velocity:** As more people work on the code, we want to make sure
  we are not wasting time dealing with merge conflicts.
- **Facilitate collaboration:** Clear standards for branching, naming, and
  committing help every team member understand the state of the codebase.
- **Minimize integration bugs:** A clear flow for contributing code makes sure
  that all changes can be tested effectively before being merged into the
  larger project.

RAMMP is a polyrepo, so this workflow applies within each repo you contribute
to. The [how-to guide](/contributing/how-to) covers how a module repo is
structured, built and published; this page covers how the code gets from your
branch into the repo.

## Pre-commit hooks

Repos that enforce code style use [pre-commit](https://pre-commit.com/) to
run formatters and linters automatically before each commit (for example Ruff
for Python, clang-format for C++, and general file hygiene). If the repo has a
`.pre-commit-config.yaml`, run `pre-commit install` once after cloning. After
that, the hooks run automatically on every `git commit`.

With `uv` (recommended):

```bash
uv tool install pre-commit
pre-commit install
```

Without `uv`:

```bash
pip install pre-commit
pre-commit install
```

<Callout type="info">
  On first run, pre-commit downloads the hook environments, which may take a
  minute. If a hook fails, it blocks the commit and shows what needs to be
  fixed. Some hooks (Ruff, clang-format) auto-fix files in place; just stage
  the changes and commit again.
</Callout>

## Repo organization

Every repo has at least two long-lived branches:

1. `main`: Fully tested, deployable code. The code on this branch should be
   stable and deployable to the robot at all times. `main` is locked and is
   only updated periodically from `dev` (except for [hotfixes](#hotfixes)).
2. `dev`: The staging ground for testing new code, and should be mostly
   stable. When contributing new code, you open pull requests (PRs) to `dev`
   with your tested code.

Feature and bug branches are your active development branches and do not need
to be stable. Every time you start a new feature, you fork a feature or bug
branch from the latest version of `dev`. You can do whatever you want in this
branch. When your feature is ready, you open a PR back to `dev`.

<Callout type="info">
  Some smaller repos may only have `main`. If there is no `dev` branch, follow
  the same workflow with `main` in its place.
</Callout>

## Contributing code

All of the features that need to be developed and bugs that need to be
squashed should be added as issues on the GitHub repo. If the code you are
working on is not listed as an issue, please open an issue before you begin
this workflow.

<Steps>

### Assign yourself to the issue on GitHub

This ensures that two people are not developing the same feature
simultaneously.

### Pull the latest changes to your local repo

In your terminal, navigate to the repo, make sure that your working tree is
clean (with `git status`), and run:

```bash
git checkout dev
git pull
```

This ensures that you are developing on the latest version of `dev`.

### Create a feature branch

Once you are on the latest `dev` branch, create a new branch for your feature
or bug fix:

```bash
git checkout -b feature/<ISSUE NUMBER>-<BRIEF-DESCRIPTION>
```

If you are working on a bug, name your branch:

```bash
git checkout -b bug/<ISSUE NUMBER>-<BRIEF-DESCRIPTION>
```

The issue number is the big number right next to the title of the issue on
GitHub. Keep branch names descriptive and concise.

### Develop and test

Work on your changes in your feature branch. Feel free to commit code (and
push to GitHub) as frequently as you'd like. Your feature branch is yours to
work in, so use it however you'd like. Make sure you are testing your code
locally on the hardware or using available simulations as applicable.

### Open a pull request

Once you have sufficiently tested your code, it's time to open a pull request
into `dev` to integrate your feature.

First, merge the latest changes in `dev` into your feature branch. This
ensures that you resolve merge conflicts before opening your pull request:

```bash
git checkout dev
git pull origin dev
git checkout <YOUR FEATURE BRANCH>
git merge dev
```

Then push your latest changes to GitHub:

```bash
git push origin <YOUR FEATURE BRANCH>
```

Finally, go to the repo on GitHub and create a new pull request from your
feature branch to `dev`. If the repo has a PR template, GitHub will offer it
when you open the PR; fill it out with a description of your changes, your
test procedure, and your results. If you include the phrase
`Closes #<ISSUE NUMBER>`, the PR is automatically linked to the issue.

Before merging a pull request, you will need to get somebody to review your
code, so go ahead and assign a relevant reviewer.

### Merge the pull request

Once you have gotten approval from the reviewers, you can merge your PR into
`dev`. Please use **Squash and Merge** so that all of your intermediate
commits don't get added to the development history on GitHub. After merging,
remember to go back to your local `dev` branch and pull the changes to start
your next feature.

</Steps>

## Hotfixes

<Callout type="warning">
  Use this only for critical bugs found in `main` that need an immediate fix.
</Callout>

If a bug is found on `main` and `dev` is currently unstable or contains
unfinished features, use a hotfix.

<Steps>

### Branch off `main`

```bash
git checkout main
git pull origin main
git checkout -b hotfix/<BRIEF-DESCRIPTION>
```

### Fix and test

Ensure it fixes the immediate problem without breaking other `main`
functionality.

### Merge to `main`

Open a PR directly to `main`. Once merged, deploy to the robot.

### Back-port to `dev`

**This step is critical.** Immediately merge the hotfix branch (or `main`)
into `dev` so the bug doesn't reappear in the next release cycle.

</Steps>

## FAQ

### Do I lose my history with Squash and Merge?

The git log on the server stays clean (one commit per feature), but the GitHub
PR preserves every individual commit and comment you made during development.
