# Development flow

RAMMP software comes from several labs, each with its own codebase and its
own dependencies, and all of it has to run together on one chair. Docker is
how that stays manageable:

- **Sharing code** is pulling an image, not building another lab's source and
  reconciling its dependencies with yours.
- **Deploying** is running the images that were tested, pinned by tag.
- **Developing** stays fast because your own code is not an image yet. It
  runs natively from `~/ros2_ws`, next to the images.

## How the pieces fit

Everything on the system is ROS 2 code, and all of it can be built and run
natively. When a piece becomes stable it is packaged into a Docker image so
that anyone can run it without building it, and so the chair runs a known
version of it. At any moment the system is therefore a mix: stable modules
running from images, and code under development running from source. Both
are on the same DDS network, so they see each other's topics without any
extra configuration.

[sheppy](/sheppy) launches and supervises both kinds. In its manifest, one
node can list an image and a workspace launch as alternatives, and a profile
selects which one runs. Moving your code from source to image is a change of
profile, not a change to the manifest.

The three workflows below are three ways to navigate that mix, depending on
what you are working on.

## The three workflows

Each has its own page with the setup and a worked example.

| | Stable modules run as | Your code runs as | When to use |
| --- | --- | --- | --- |
| [Hybrid](/development/hybrid) | Images, under sheppy | Native, from `~/ros2_ws` | Day to day. The recommended workflow. |
| [Fully native](/development/native) | Native, cloned into `~/ros2_ws` | Native | Changing a stable module itself, or a machine that cannot pull images. Not recommended otherwise. |
| [Deployment](/development/deployment) | Images, under sheppy | An image, under sheppy | Checking a module is ready to ship. This is what the chair runs. |

**Hybrid.** The stable stack comes up with one `sheppy up`, pinned to the
same versions every other lab runs, and your code stays in the native build
loop.

**Fully native.** Every line of the stack is in your workspace and you can
change any of it. In exchange you build and maintain other labs' code, and
your stack drifts from the pinned images the chair runs. Use it when the
hybrid workflow cannot do what you need.

**Deployment.** The hybrid workflow with your node switched to its image
alternative, so that "works on my machine" and "works on the chair" are the
same test. Run it before you open the pull request that publishes your
module.

The [recommended git workflow](/git-workflow) applies throughout: every
change to every repo arrives through a reviewed pull request.
