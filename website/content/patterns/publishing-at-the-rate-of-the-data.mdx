# Publishing at the rate of the data

A publisher decides how much every subscriber pays. On the Orin, each message
costs a Python subscriber 1.5 to 2 ms whether or not the value changed, so a
node that republishes the same numbers from a fast timer spends other nodes'
CPU as well as its own.

The base control node is the example to keep in mind. Its Teensy sends
telemetry at a fixed 10 Hz. The node polled the serial port from a 1 kHz
timer, republished joint and chair state from two 100 Hz timers, and sent the
LUCI joystick from a 200 Hz timer. Most of a core went to relaying 10 Hz of
data.

This page is the convention for how often a node reads, publishes and logs.

## The convention

Never loop faster than the source. If a device delivers data at a rate, read
it at that rate and publish it when it arrives.

- **Block on the source instead of polling it.** A thread that sits in
  `serial.readline()` wakes exactly when a line arrives. A timer that checks
  `in_waiting` a thousand times a second wakes a thousand times a second.
- **Publish on arrival.** When telemetry comes in, convert it and publish it
  in the same callback. Do not cache it for a timer to re-send.
- **Gate loops on a new stamp.** Head perception ran MediaPipe 240 times a
  second on a 15 Hz camera until it started comparing the frame's header stamp
  with the last one it processed.

**State goes out on change, with a slow keepalive.** State that changes
rarely, such as the system state machine or the set of allowed GUI commands,
is published when it changes and then once a second, so a late subscriber
still gets it and a consumer can tell a quiet publisher from a dead one. The
timer that checks for a change can run at 10 Hz; the message does not.

```python
def publish_system_state(self):
    msg = self._build_state()
    key = (msg.state, list(msg.supported_user_inputs))
    now = time.monotonic()
    if key != self._last_published or now - self._last_publish_time >= 1.0:
        self._pub.publish(msg)
        self._last_published = key
        self._last_publish_time = now
```

**Inputs are forwarded as they arrive, and the keepalive skips a tick when
something was just sent.** The LUCI chair needs its remote joystick above
10 Hz or it engages the brakes. The base node forwards the user's joystick the
moment it arrives and runs a 50 Hz keepalive that skips its tick when
something went out in the last period. The user's input has no added latency,
and an autonomous drive command waits at most 20 ms.

**The wire rate is chosen for the consumers.** A feedback loop can run faster
than it publishes. The arm driver reads the Kortex arm at 100 Hz because its
collision check and comms watchdog need that, and publishes joint states and
end-effector topics on every other read. Nothing downstream consumes faster
than 20 Hz: the GUI updates its model at 10 Hz, system_control edge-detects
the gripper, the door controller samples force at 20 Hz, and
`robot_state_publisher` throttles TF on its own.

<Callout type="warning">
  Lowering a published rate is the one change on this page that a subscriber
  can see on the wire. Check every subscriber first, say what you found in the
  PR, and keep the internal loop at its original rate. Removing a republish of
  unchanged values is not a rate change and needs no such review.
</Callout>

**Logs follow the same rule.** A log line per message is a publish per message
to a slow subscriber. The LUCI gRPC node logged one INFO line per joystick
message and per camera frame, and the `ros2 launch` wrapper relaying those
lines cost 12% of a core on its own. Log on change, on error, or with
`throttle_duration_sec`. If the node is not yours, set its log level in the
launch file.

## A module that does this

The base control node in Demo-Software (`hardware/rammp_prototype_driver`):

- A daemon thread blocks in `readline()` on the Teensy's serial port.
- `handle_serial_line` publishes joint and chair state when a `TELEMETRY`
  line arrives.
- `_send_joystick_keepalive` sends only when the user has been quiet for a
  period.

With the chair off, the node went from 93% of a core to 15%. See
[Demo-Software #263](https://github.com/rammp-org/Demo-Software/pull/263) for
the rest of the measurements.

## What does not belong here

- **A timer in place of a callback.** If the data is in a callback, publish it
  there. A timer is for work that has no natural trigger.
- **A sleep in a callback to wait for data.** It blocks an executor thread and
  the data still arrives through the executor. Subscribe to it instead.
- **A small message published fast.** The subscriber's cost is per message,
  not per byte. A 100 Hz `Bool` costs as much as a 100 Hz `JointState`.
