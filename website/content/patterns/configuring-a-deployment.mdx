# Configuring a deployment

A deployment is configured in several places: the sheppy manifest, its
profiles, the module images, a module's saved state, and the robot itself.
This page says which place each kind of setting goes in, so a value is set in
one place only.

## Where each setting goes

| Setting                                     | Where it goes                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Which alternative of a node runs            | the manifest's `alternatives`, and a profile's `selections`                                                      |
| A node parameter and its default            | the alternative's `params:` in the manifest                                                                      |
| A parameter value for one robot             | that robot's profile, `profiles/<robot>.yaml`, under `overrides`                                                 |
| A parameter value for one run               | `p` in the TUI                                                                                                   |
| Large configuration that rarely changes     | the module's image                                                                                               |
| A value the module saves and reloads        | `~/.config/<module>`, mounted at `/config` (see [Storing state across runs](/patterns/storing-state-across-runs)) |
| Host and device setup that sheppy cannot do | `config/robots/<robot>/` next to the manifest, applied by a script                                               |

### Parameters

Put a parameter in `params:` if anyone might change it for a robot or from the
TUI. A profile override or a TUI edit only applies to a parameter listed
there. A value hard-coded in `command:` can only be changed by editing the
manifest.

### Robot setup

Some setup has to be done before any node starts, and sheppy has no way to do
it: the host's network interfaces, or the network settings a camera stores on
the device. That goes in `config/robots/<robot>/`, one file per kind of
setup. Each file has a script that applies it. The script:

- checks the whole file before it changes anything;
- changes only what differs, so running it twice is safe;
- has `--dry-run`, which prints the changes without making them;
- has `--validate`, which checks the file and exits. CI runs it on every
  robot.

Use the same robot name in `config/robots/<robot>/` and in
`profiles/<robot>.yaml`.

## Example: flatbot

flatbot is a mobile test platform. Its setup lives in rammp-deployments, in
`december_2026/config/robots/flatbot/`:

- `network.yaml` sets the Jetson's two network interfaces: a static address
  on the link to the arm, and DHCP on the sensor network.
- `oak_d.yaml` sets the network config of each OAK-D PoE camera. Each entry is
  named after the camera's node in the manifest, and the script finds the
  camera by its device ID.

After the Jetson is reflashed, two commands restore the setup:

```bash
uv run scripts/network_config.py december_2026/config/robots/flatbot
uv run scripts/oak_d_config.py   december_2026/config/robots/flatbot
```

## What does not go in `config/robots/`

- **Node parameters.** They go in the manifest's `params:` and in profiles.
- **Config files for nodes.** A separate config directory can't be overridden
  from a profile or the TUI. Ship large config in the module's image instead.
- **Saved state**, such as a calibration the operator ran. See
  [Storing state across runs](/patterns/storing-state-across-runs).
- **Secrets.**
