# Subscribing only while working

Most of the chair's nodes spend most of their time waiting. The door opener
waits for a door, the drink node waits for an order, the detector waits to be
enabled. A node that keeps its camera, arm-state and TF subscriptions open
while it waits pays for every message that arrives, whether or not anything
reads it. Across the chair, those idle subscriptions were costing more than
four of the Jetson's eight cores.

This page is the convention for what a node may subscribe to while nothing
has asked it to work.

## Why a message is not free

On the Orin, a Python node with a `MultiThreadedExecutor` spends roughly
1.5 to 2 ms of CPU on every delivered message before the callback runs. The
executor wakes, rebuilds its wait set, deserializes the message and hands it
to a thread. A callback that only stores the message still pays all of that.

So a single 100 Hz topic costs a Python subscriber 15 to 20% of a core, and
three 15 Hz camera topics plus `/tf` cost about a third of a core before any
work is done on them.

## The convention

A node that has not been asked to do anything subscribes to nothing that
arrives faster than about 1 Hz. Sensors, arm state and TF are subscribed when
work starts and dropped when it ends.

Give each interface that wraps a stream a `start()` and a `stop()`, both
idempotent, and call them from whatever marks the start and end of work:

- **An enable service** creates the subscriptions on `True` and destroys them
  on `False`. The door button detector does this in its
  `/arm/door/detection/enable` handler, for the RGB and depth images, both
  `camera_info` topics and its `TransformListener`.
- **An action** creates them when the goal is accepted and destroys them in a
  `finally` block, so a cancel or an exception also releases them. The door
  push controller subscribes to the arm's 100 Hz force and velocity topics for
  the length of one `/arm/door/open` goal.
- **Several overlapping users** share a reference count under a lock. The
  subscriptions come up with the first user and go down with the last.

```python
def _acquire_sensors(self):
    with self._sensor_lock:
        self._sensor_users += 1
        if self._sensor_users == 1:
            self.camera.start()
            self.arm.start()

def _release_sensors(self):
    with self._sensor_lock:
        self._sensor_users -= 1
        if self._sensor_users == 0:
            self.camera.stop()
            self.arm.stop()
```

`stop()` destroys the subscriptions with `destroy_subscription`, calls
`unregister()` on a `tf2_ros.TransformListener`, and clears the cached data so
a later reader cannot mistake a stale frame for a fresh one.

## Plan for the warm-up

Data that used to be waiting in a cache now arrives a moment after `start()`.
The delays are small, but the code has to expect them:

- **A camera frame** arrives within one camera period, about 70 ms at 15 Hz.
  A pipeline on a 5 Hz timer sees it before its next tick.
- **Arm state** arrives within one publish period, 20 ms at 50 Hz. A command
  loop that reads the latest joint state treats `None` as "not yet", not as
  "reached".
- **TF** needs two samples on each side of a stamp before a lookup at that
  stamp succeeds, about 80 ms with the arm's state publisher. A per-frame
  lookup that already returns `None` on failure and retries next frame needs
  no change.
- **Transient-local topics** (`/tf_static`, extrinsics, `/robot_description`)
  arrive at once on subscribe and cost nothing afterwards. They can stay
  subscribed for the life of the node.

A reader of the cache skips the sample when the cache is empty; it does not
raise. `perceive_cup_info` in the drink node does `continue` when no frame has
arrived. Before that guard, the first two streaming ticks after enable each
logged an exception.

<Callout type="info">
  Keep a warm start if the first real call has to be fast. The drink node runs
  MediaPipe on ten frames at launch so the first mouth detection is not a cold
  model load. It calls `start()` for that, and `stop()` right after.
</Callout>

## What still costs something

Two things remain after the subscriptions are gone, and both are cheap:

- **Timers below about 10 Hz.** A 5 Hz processing timer that returns at once
  when disabled is under 1% of a core.
- **Status topics at 1 Hz** such as `/arm/status`, `/diagnostics`, and the GUI
  connection flag.

An idle node that follows this page sits under 2% of a core.

## A module that does this

The drink node in Demo-Software (`demo_modules/cornell_feeding`):

- Its camera interface and arm client each expose `start()` and `stop()`.
- The action server reference-counts them around every action and around
  cup-handle streaming, with the `_acquire_sensors` and `_release_sensors`
  pair above.
- The head-perception warm start calls `start()` for itself and `stop()`
  right after.

Idle, the node went from 58% of a core to under 1%. See
[Demo-Software #263](https://github.com/rammp-org/Demo-Software/pull/263) for
the measurements on the other nodes.

## What does not belong here

- **Throttling inside the callback.** Dropping nine messages out of ten in
  Python still pays the executor cost for all ten. Either the publisher sends
  less, or the subscriber is not there.
- **A subscription kept open so the data is buffered and ready.** The buffer
  costs more than the 70 ms it saves, and the first frame after enable
  arrives before anyone can notice.
- **Polling `rclpy.spin_once` from a callback** to fetch fresh data. It
  detaches the node from its executor and delivery stops. See
  [Waiting without spinning](/patterns/waiting-without-spinning).
