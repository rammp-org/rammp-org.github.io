# Common patterns

Conventions that every RAMMP module follows. A module written in one lab
then behaves the way the others expect when it runs on the chair. Each page
describes one pattern: the problem, the convention, and a module that already
uses it.

## Pages

- **[Storing state across runs](/patterns/storing-state-across-runs)** — where a
  module keeps a value that has to survive a container restart, and how it
  copes when that value is gone.
- **[Subscribing only while working](/patterns/subscribing-only-while-working)** — a
  node that has not been asked to work subscribes to nothing fast; sensors and
  arm state come and go with the task that needs them.
- **[Publishing at the rate of the data](/patterns/publishing-at-the-rate-of-the-data)**
  — block on the source instead of polling it, publish on arrival or on change
  with a slow keepalive, and pick the wire rate for the consumers.
- **[Separating bulk data from control traffic](/patterns/separating-bulk-data-from-control-traffic)**
  — a button press never waits behind video; separate channels, send on
  change, and bound the worst-case frame.

- **[Starting without the hardware](/patterns/starting-without-the-hardware)**
  — launch order never matters; a missing peer is logged, retried on a timer,
  and served around, and losing it later is handled the same way.
- **[Waiting without spinning](/patterns/waiting-without-spinning)** — one
  executor drives the node; callbacks wait on cached state with a sleep and a
  deadline, never by spinning or blocking on a terminal.
- **[Reporting one frame at a time](/patterns/reporting-one-frame-at-a-time)**
  — perception messages describe one frame, carry its stamp, publish absence
  explicitly, and filters follow a sustained change.
