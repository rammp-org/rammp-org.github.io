# Developer setup

This page takes a Jetson from a blank board to a machine that runs the RAMMP
system and builds modules for it: flash it, make it real-time, install Docker
and sheppy, and bring the system up once. Each step says what has to be true
and links to the document that walks you through it; it does not repeat
NVIDIA's or Docker's instructions.

The board itself is described on [RAMMP Gen 1.5](/platform#compute). The
versions it has to run are on [Software versions](/software#versions).

## Before you start

- A **Jetson AGX Orin** — the chair's own, or a development board. Both are
  set up the same way.
- An **x86 Ubuntu host** to flash it from. NVIDIA's SDK Manager runs neither
  on the Jetson itself nor on a Mac.
- A **1 TB NVMe SSD**, fitted before you flash. The chair's is a WD_BLACK
  SN7100 (`WDS100T4X0E`).
- A clone of
  [`rammp-deployments`](https://github.com/rammp-org/rammp-deployments) on the
  Jetson once it boots. It holds the host scripts below and the chair's
  manifest:
  ```bash
  git clone git@github.com:rammp-org/rammp-deployments.git ~/rammp-deployments
  ```

<Callout type="info">
  Not touching the GPU or the arm? `rammp-base` runs on any arm64 host with
  Docker — an ARM Mac inside an arm64 Linux VM, or an AWS Graviton instance —
  so you can skip straight to [Docker](#docker). It will not run on an x86
  machine: there is no amd64 variant, and you get `exec format error`.
</Callout>

## The Jetson

<Steps>

### Fit the SSD

Into the dev kit's M.2 Key M slot —
[Developer Kit user guide](https://developer.nvidia.com/embedded/learn/jetson-agx-orin-devkit-user-guide/index.html).
Do it now: adding the drive after flashing means flashing again, or migrating
Docker's `data-root` by hand.

### Flash JetPack to the NVMe

From the x86 host, with
[SDK Manager](https://developer.nvidia.com/sdk-manager). Pick JetPack
**6.2.1**, which is Jetson Linux r36.4.7, and NVMe as the storage target, so
the root filesystem and Docker's image store live on the drive from the
start. Do not pick a newer JetPack: NVIDIA ships a prebuilt PREEMPT_RT kernel
for r36.4 and not for r36.5, and the next step depends on it. A board already
on JetPack 6.0 must be reflashed: its driver predates the CUDA 12.6 runtime in
`rammp-cuda` —
[Jetson Linux quick start](https://docs.nvidia.com/jetson/archives/r36.4/DeveloperGuide/IN/QuickStart.html).

### Install the real-time kernel

On JetPack 6 it is an apt package set, not a flash option. The packages live
in a separate NVIDIA repository that a fresh flash does not know about, so add
it first:

```bash
echo "deb https://repo.download.nvidia.com/jetson/rt-kernel r36.4 main" \
  | sudo tee -a /etc/apt/sources.list.d/nvidia-l4t-apt-source.list
sudo apt update
sudo apt install nvidia-l4t-rt-kernel nvidia-l4t-rt-kernel-headers \
  nvidia-l4t-rt-kernel-oot-modules nvidia-l4t-display-rt-kernel
```

The install adds a `real-time` entry to `/boot/extlinux/extlinux.conf` next
to the stock `primary` one. Open the file and make sure it says
`DEFAULT real-time`: NVIDIA's kernel packages set `DEFAULT` to whichever
kernel they configured last, and that is not always the real-time one.
Reboot, then confirm —
[Real-Time Kernel Using OTA Update](https://docs.nvidia.com/jetson/archives/r36.4/DeveloperGuide/SD/Kernel/KernelCustomization.html#real-time-kernel-using-ota-update).

```bash
head -1 /etc/nv_tegra_release   # "# R36 (release), REVISION: 4.7"
uname -r                        # ends in -rt-tegra
cat /sys/kernel/realtime        # 1
```

### Set the power model to MAXN

`sudo nvpmodel -m 0`, then `sudo jetson_clocks` —
[Power and performance](https://docs.nvidia.com/jetson/archives/r36.4/DeveloperGuide/SD/PlatformPowerAndPerformance/JetsonOrinNanoSeriesJetsonOrinNxSeriesAndJetsonAgxOrinSeries.html).

### Isolate the real-time core

Append `isolcpus=11 nohz_full=11 rcu_nocbs=11` to the `APPEND` line of the
`real-time` label in `/boot/extlinux/extlinux.conf`, check that
`DEFAULT real-time` is still set, and reboot. Core 11 is the highest-numbered
core on the AGX Orin; the arm's control loop is pinned there. Leave the
`primary` label untouched so a typo does not leave the board unbootable, and
do this at the console, not over SSH —
[rt-tuning §B](https://github.com/rammp-org/kinova-gen3-driver/blob/main/docs/rt-tuning.md#b-boot-time-tunings-kernel-cmdline--needs-a-reboot).

### Grant real-time privileges once

Real-time processes run without `sudo`. They need `rtprio` and `memlock`
limits and a udev rule for `/dev/cpu_dma_latency`:

```bash
sudo ~/rammp-deployments/scripts/rt_grant_once.sh
```

Log out and back in afterwards.

### Apply the runtime tunings

```bash
sudo ~/rammp-deployments/scripts/rt_setup.sh 11
```

It sets the `performance` governor, locks clocks, disables deep idle, removes
RT throttling, pins timers and turns off transparent huge pages.

<Callout type="warning">
  These reset on reboot. Make them stick with the systemd unit next to the
  script: copy `scripts/rt-setup.service` to `/etc/systemd/system/`, point its
  `ExecStart` at your clone, and `sudo systemctl enable --now rt-setup.service`.
</Callout>

### Check that it holds

A PREEMPT_RT kernel is necessary but not sufficient; every row below has to
be true, or the tail latency comes back. The reasoning behind each is in the
driver's
[real-time tuning guide](https://github.com/rammp-org/kinova-gen3-driver/blob/main/docs/rt-tuning.md).

| Setting | Must be | Check |
| --- | --- | --- |
| Kernel | PREEMPT_RT | `cat /sys/kernel/realtime` → `1`, and `uname -r` ends in `-rt-tegra` |
| Power model | MAXN — all cores, no power cap | `sudo nvpmodel -q` |
| CPU governor | `performance` on the RT core | `cat /sys/devices/system/cpu/cpu11/cpufreq/scaling_governor` |
| Clocks | locked at maximum | `sudo jetson_clocks --show` |
| Core isolation | core 11 reserved for the control loop | `grep -o 'isolcpus=[^ ]*' /proc/cmdline` → `isolcpus=11` |
| Deep CPU idle | disabled on the isolated core | `cat /sys/devices/system/cpu/cpu11/cpuidle/state1/disable` → `1` |
| RT throttling | off | `cat /proc/sys/kernel/sched_rt_runtime_us` → `-1` |
| Timer migration | off | `cat /proc/sys/kernel/timer_migration` → `0` |
| Transparent huge pages | `never`, or the file absent | `cat /sys/kernel/mm/transparent_hugepage/enabled` |

Then measure:

```bash
sudo apt install rt-tests
sudo taskset -c 11 cyclictest -m -t1 -p 90 -i 1000 -D 60
```

The maximum latency to accept, and what to look for in the output, are in
[rt-tuning §D](https://github.com/rammp-org/kinova-gen3-driver/blob/main/docs/rt-tuning.md#d-validate--measure-dont-assume).

</Steps>

## Docker

Every module runs as a container, and the base images assume the host's
Docker matches the chair's. Install Docker Engine **27.5.1**, the version on
[Software versions](/software#versions), from Docker's apt repository. Their
guide has a section on installing a specific version:
[Install Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
Then add yourself to the `docker` group so it runs without `sudo`:
[Linux post-installation steps](https://docs.docker.com/engine/install/linux-postinstall/).

The NVIDIA Container Runtime comes with JetPack; nothing to install. Confirm
Docker can see it, then that a base image can see the GPU:

```bash
docker info | grep -i runtimes                              # lists nvidia
docker run --rm --runtime nvidia --network host --ipc host \
  ghcr.io/rammp-org/rammp-cuda:1.0.0-jp6 \
  python3 -c 'import torch; print(torch.cuda.is_available())'   # True
```

What each flag is for, and how modules are built on that image, is in the
[Build and publish](/publishing/build-and-publish#run-it-on-the-robot) page.

## Shell environment

Two variables belong in every shell on the Jetson, and in the shell you SSH
in from. Run the line below on both machines. `RMW_IMPLEMENTATION` selects Cyclone DDS, which the base images run;
a host shell on the default RMW only partly discovers the containers.
`COLORTERM` gives the sheppy TUI its full palette over SSH, which does not
forward it.

```bash
for rc in ~/.bashrc ~/.zshrc; do [ -f "$rc" ] && ! grep -q RMW_IMPLEMENTATION "$rc" && printf '\nexport RMW_IMPLEMENTATION=rmw_cyclonedds_cpp\nexport COLORTERM=truecolor\n' >> "$rc"; done; true
```

It appends to whichever of the two files exist, once. Open a new shell
afterwards. The Cyclone RMW package itself comes with the
host ROS 2 install: `sudo apt install ros-humble-rmw-cyclonedds-cpp` if
`ros2 doctor` reports it missing.

## sheppy

[sheppy](/sheppy) launches and supervises every module on the chair. One
line installs it —
[Getting started → Install](/sheppy/getting-started#install) — and puts
`sheppy` and `sheppyd` on your `PATH`.

## Workspace

Your code lives in `~/ros2_ws`, with the shared message types cloned into it
at the tag on [Software versions](/software#versions). Install ROS 2 Humble
first, with `colcon` and `rosdep`, following
[the ROS 2 install guide](https://docs.ros.org/en/humble/Installation/Ubuntu-Install-Debs.html).

```bash
mkdir -p ~/ros2_ws/src && cd ~/ros2_ws/src
git clone --branch v1.0.0 https://github.com/rammp-org/rammp-interfaces-ros2.git
cd ~/ros2_ws && rosdep install --from-paths src --ignore-src -y && colcon build
```

How to develop in it is the [hybrid workflow](/development/hybrid).

## First run

The chair's manifest is in the `rammp-deployments` clone from
[Before you start](#before-you-start). Source your workspace, go to the
deployment's directory, and open sheppy there:

```bash
source ~/ros2_ws/install/setup.bash
cd ~/rammp-deployments/december_2026
sheppy
```

The TUI opens on that manifest. Start nodes by hand from there — the keys
are in [the 90-second walkthrough](/sheppy/getting-started#the-90-second-walkthrough).
