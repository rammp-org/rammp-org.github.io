## Compute

One NVIDIA Jetson runs everything on the chair: the arm driver, the base,
perception, and every module.

| | |
| --- | --- |
| Module | [NVIDIA Jetson AGX Orin 64GB Developer Kit](https://developer.nvidia.com/embedded/learn/get-started-jetson-agx-orin-devkit) |
| SoC | Tegra234 — 12 Arm Cortex-A78AE cores, Ampere GPU at compute capability `sm_87` |
| Memory | 64 GB, shared between CPU and GPU |
| Storage | WD_BLACK SN7100 1 TB NVMe SSD (`WDS100T4X0E`), M.2 2280, PCIe Gen4, in the dev kit's M.2 Key M slot |

- The GPU is the target of the [`rammp-cuda`](/publishing/base-images#rammp-cuda)
  base image.
- The NVMe is required: the 64 GB eMMC cannot hold `rammp-cuda` (several GB),
  one image per module on top of it, and a second tag of each during upgrades.

### Real-time

| Loop | Deadline |
| --- | --- |
| Kinova Gen3 low-level driver | 1 kHz torque loop over Ethernet; a missed cycle trips the arm's watchdog and faults the arm |
| Base actuation | Its own deadline |

Both need bounded wake-up latency, so the Jetson runs a PREEMPT_RT kernel with
one core isolated for the control loop. Kernel version:
[Software versions](/software#versions). Settings and how to apply them:
[Developer setup](/setup#the-jetson).

### Cameras

The RGBD cameras match flatbot's. Both are Luxonis OAK PoE units: power and
data over one Ethernet cable (no USB runs), depth computed on the camera.

| Node | Camera | Key property |
| --- | --- | --- |
| `scene_camera` | [OAK-D Pro W PoE](https://docs.luxonis.com/hardware/products/OAK-D%20Pro%20W%20PoE), OV9782 colour variant | 127° horizontal field of view: the table and the arm's whole workspace |
| `wrist_camera` | [OAK-D Pro PoE](/oak-d-pro-poe) | Active stereo, near-field tuned, minimum depth about 15–30 cm |

- Both run the `rammp-suite-software/oak` image with different parameters.
- Each node finds its camera by device ID (MxID); the address can change under
  DHCP without a manifest edit.
- Laptop setup: [OAK-D Pro PoE](/oak-d-pro-poe).

## Frames and transforms

```text
base_link (chair)
└── arm_mount                  level with the chair, X forward, Z up
    ├── scene_camera           static TF, from transforms/
    └── arm_base_link          mount rotation, from mount.yaml
        └── arm_shoulder_link → … → arm_end_effector_link
                                    ├── arm_tool_frame
                                    └── wrist_camera   static TF, from transforms/
```

- **`arm_mount`**: frame of all Cartesian goals and arm state. Same origin as
  `arm_base_link`, level with the chair, so +Z is up rather than along the
  plate. Level with the chair, not gravity: it tilts on a ramp.
- **Arm frames** use an `arm_` prefix; the chair owns `base_link`.
- **Camera frames** root each driver's own tree: `<camera>` for an OAK (the
  colour sensor, body axes), `<camera>_link` for a Gemini or RealSense.
- **`base_link` → `arm_mount`** is not published until a chair URDF owns the
  chair's fixed geometry.

### Where each transform comes from

Per robot, in `rammp-deployments/<deployment>/config/robots/<robot>/`:

| File | Sets | Read by |
| --- | --- | --- |
| `mount.yaml` | Rotation from `arm_mount` to `arm_base_link`, as `rpy_deg` | `arm_state_publisher`, which renders the arm's model and publishes `/arm/robot_description`; the driver and cuRobo read the model from that topic |
| `transforms/*.yaml` | Camera mounts and other fixed frames, in [rammp-calibration](https://github.com/rammp-org/rammp-calibration)'s `mounts.yaml` format | The `static_tf` node from [rammp-tools](https://github.com/rammp-org/rammp-tools), which publishes them on `/tf_static` |

- `scripts/set_robot.py` points `config/robots/current` at the host's robot;
  nodes read that directory.
- A solved calibration replaces a `transforms/` file as-is.

Gen 1.5 mount:

```yaml
# config/robots/gen_1_5/mount.yaml
robot: gen_1_5
rpy_deg: [0.0, 30.0, 0.0] # new_adapter_plate_v3: 30° forward lean
```

> **Fill in** `gen_1_5/transforms/` once the cameras are on the chair. Until
> then, use flatbot's below.
